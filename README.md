# Wallet Service

REST API сервис для управления балансом кошельков: пополнение, списание и получение текущего баланса. Построен на принципах чистой архитектуры с акцентом на корректность при конкурентной нагрузке.

## Стек технологий

- **Go** — язык реализации
- **Gin** — HTTP-фреймворк
- **PostgreSQL** — хранилище данных
- **pgx (v5)** — драйвер и пул соединений к PostgreSQL
- **golang-migrate** (`//go:embed`) — миграции, встроенные в бинарник
- **logrus** — логирование
- **mockery** — генерация моков для тестов
- **testcontainers-go** — интеграционное тестирование с реальным PostgreSQL
- **k6** — нагрузочное тестирование
- **Docker / docker-compose** — контейнеризация и локальный запуск

## Архитектура

Проект следует принципам чистой архитектуры с разделением на слои:

```
internal/
├── presentation/          # HTTP-слой: парсинг запросов, маппинг DTO ↔ доменная модель, HTTP-коды
├── domain/
│   └── balance/
│       ├── service/   # Бизнес-логика (интерфейсы IWalletService и т.д.)
│       └── models/    # Доменные модели
├── repository/        # Слой доступа к данным (репозиторий), работа с pgx
├── core/              # Общие sentinel-ошибки домена
migrations/            # SQL-миграции, встроенные через go:embed
loadtest/               # Скрипты k6 для нагрузочного тестирования
```

Каждая граница между слоями (Request → Model, Model → DB, Model → Response) имеет собственный маппер — доменный слой не зависит от деталей HTTP или персистентности.

## Схема данных

Хранение построено по принципу **append-only ledger**: баланс не хранится как отдельное мутируемое поле, а вычисляется как сумма всех транзакций кошелька.

Такой подход даёт полный аудит операций.

## Конкурентная безопасность

Ключевое требование — корректная работа при высокой конкурентной нагрузке на **один и тот же кошелёк** (до 1000 RPS).

Поскольку отдельной таблицы `wallets` нет, синхронизация конкурентных списаний реализована через **PostgreSQL advisory lock**:

```sql
SELECT pg_advisory_xact_lock(hashtext($1));
```

Блокировка берётся по `wallet_id` в начале транзакции списания, до расчёта текущего баланса, и автоматически снимается при `COMMIT`/`ROLLBACK`. Это гарантирует:

- баланс никогда не уходит в отрицательное значение при гонке конкурентных списаний;
- отсутствие ошибок `40001 (serialization_failure)` — запросы встают в очередь на уровне блокировки, а не конфликтуют постфактум;
- операции пополнения (`AddDeposit`), не требующие проверки баланса, выполняются без блокировок и полностью параллельно.

Под нагрузкой на один кошелёк throughput ограничен временем одной транзакции (лок → чтение суммы → вставка) — это ожидаемое и корректное поведение при строгой консистентности, а не деградация.

## Быстрый старт

### 1. Настройка окружения

```bash
cp config.env.example config.env
```

Заполни `config.env` своими значениями (см. описание переменных ниже).

### 2. Запуск через docker-compose

```bash
docker compose up --build -d
```

Поднимет сервис на `http://localhost:8080` и PostgreSQL. Миграции применяются автоматически при старте приложения (встроены в бинарник через `go:embed`).

### Переменные окружения (`config.env`)

| Переменная         | Описание                                  |
|--------------------|--------------------------------------------|
| `APP_PORT`         | Порт, на котором слушает приложение         |
| `POSTGRES_USER`     | Пользователь PostgreSQL (для образа БД)     |
| `POSTGRES_PASSWORD` | Пароль PostgreSQL (для образа БД)           |
| `POSTGRES_DB`       | Имя базы данных (для образа БД)             |
| `DB_HOST`           | Хост БД (`postgres` внутри docker-сети)     |
| `DB_PORT`           | Порт БД                                     |

## API

| Метод | Путь                 | Описание                                  |
|-------|----------------------|--------------------------------------------|
| POST  | `/wallet`            | Пополнение баланса кошелька                |
| GET   | `/wallets/:walletID` | Получение текущего баланса кошелька         |

### Коды ответов

| Код | Условие                                             |
|-----|------------------------------------------------------|
| 200 | Операция выполнена успешно                            |
| 400 | Некорректный формат запроса (невалидный UUID, пустое тело и т.п.) |
| 404 | Кошелёк не найден                                     |
| 422 | Недостаточно средств для списания                     |
| 500 | Непредвиденная ошибка сервера                          |

## Тестирование

Проект использует два уровня тестов:

### Юнит-тесты

Мокают зависимости через `mockery` (сервис/репозиторий).

### Интеграционные тесты

Поднимают реальный PostgreSQL в Docker через `testcontainers-go`, применяют миграции и проверяют поведение репозитория и конкурентную безопасность против настоящей БД.

### Покрытие тестами

```bash
make coverage
```

Сгенерирует `coverage.html` с построчной подсветкой покрытого/непокрытого кода.

## Нагрузочное тестирование

Скрипты `k6` в директории `loadtest/` проверяют устойчивость сервиса при высокой конкурентной нагрузке на один кошелёк (1000 RPS), согласно требованию ТЗ.

```bash
docker run --rm -i \
  --network wallet-app_app-network \
  -v $(pwd)/loadtest:/scripts \
  grafana/k6 run /scripts/load-test-single-wallet.js
```

Ожидаемый результат: при высокой конкуренции на один кошелёк сервис не возвращает 5xx-ошибок, а баланс никогда не уходит в отрицательное значение — операции корректно сериализуются на уровне advisory lock, latency растёт по мере роста очереди, но данные остаются консистентными.

## Миграции

Миграции лежат в `migrations/` и встроены в бинарник через `go:embed` — не требуют внешнего CLI или монтирования файлов в проде.
